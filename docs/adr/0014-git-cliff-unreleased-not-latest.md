# ADR-0014: git-cliff uses `--unreleased`, tags pin to the commit CI ran on

Status: Accepted
Date: 2026-08-31

## Context

Every release generated by the pipeline described in
[ADR-0009](./0009-version-bump-triggered-release.md) shipped changelog and
release-note content for the **previous** release, not the one actually
being published. `sdk-v3.3.0`'s GitHub Release body described `sdk-v3.2.0`'s
commits; `mcp-v0.2.2`'s described `mcp-v0.2.0`'s. This went unnoticed through
nine releases because nothing failed — the wrong content still rendered
successfully and still looked plausible.

Root cause: `.github/actions/release-prepare/action.yml` ran
`git-cliff --tag <prefix><version> --latest`. `--latest` selects commits
since the newest **already-existing** git tag, and `--tag` only relabels
that selection — it doesn't change which commits are chosen. But the tag
for the version being released doesn't exist yet at this point in the job;
it's created later, by `Create GitHub Release`
(`softprops/action-gh-release`, `release-sdk.yml`/`release-mcp.yml`). So
`--latest` always resolved to the release before the one being published,
and `--tag` just stuck the new version's label on the old content.

Reproduced directly against the repo's pinned git-cliff 2.13.1:

```
$ pnpm exec git-cliff --tag sdk-v3.4.0 --tag-pattern '^(sdk-)?v[0-9].*' \
    --include-path 'packages/sdk/**' --latest
WARN git_cliff > There is already a tag (sdk-v3.3.0) for f95045c...
## [sdk-v3.3.0] - 2026-08-31      <- asked for 3.4.0, got 3.3.0's commits
```

The failure mode is a `WARN`, not an error — exit code 0 — which is why CI
never flagged it.

A second, independent issue compounds this: the release workflows'
`actions/checkout` didn't pin a `ref`, so under the `workflow_run` trigger it
checked out whatever `main` happened to be at job-start time, not the commit
CI actually validated. `Create GitHub Release` then tagged that same
drifted checkout. `mcp-v0.2.0` ended up tagging an SDK changelog-bot commit
that landed on `main` 85 seconds after the real `mcp` release commit, purely
because the SDK release job's push won the race.

## Decision

- `release-prepare`'s two git-cliff invocations use `--unreleased`
  ("commits not yet belonging to a tag") instead of `--latest`. This is
  correct for the normal case, where the new tag genuinely doesn't exist
  yet. The one case `--unreleased` doesn't cover — resuming a
  `force_publish` release after `Create GitHub Release` already created the
  tag on a prior, partially-failed attempt — is detected by checking
  whether `refs/tags/<prefix><version>` already exists; if so, the step
  falls back to `--latest`, which is correct _in that specific case_
  because the tag it resolves to is now the one being resumed, not the
  previous release.
- The same swap applies to the local preview scripts
  (`changelog:sdk`/`cli`/`mcp` in the root `package.json`), so
  `pnpm changelog:sdk` matches what CI will actually produce.
- If the selected range has no commits after `--include-path` filtering, the
  step now detects the empty render and skips writing to `CHANGELOG.md`
  instead of prepending a bare, content-free heading.
- Both release workflows now pin `actions/checkout`'s `ref` and
  `Create GitHub Release`'s `target_commitish` to
  `github.event.workflow_run.head_sha` (falling back to `github.ref`/
  `github.sha` for `workflow_dispatch`, which has no `workflow_run` event to
  read a `head_sha` from). The tag now always lands on the commit CI
  actually ran against.

## Consequences

- Every release from here on describes its own diff. Nothing about the
  `--include-path` scoping that motivated `--latest` in the first place
  changes — that comment's reasoning about per-tag bucketing was correct,
  it was the chosen flag that was wrong.
- The nine pre-existing releases (`v3.0.0` through `mcp-v0.2.2`) are not
  self-correcting — their tags and GitHub Release bodies were written under
  the old behavior and are fixed as a one-time backfill, not by this change.
  `CHANGELOG.md` in both packages is repaired directly; GitHub Release
  bodies are rewritten via `gh release edit` using the same corrected
  `--unreleased`-based ranges. Old tags are not moved or recreated — npm
  provenance and Docker image labels reference them by name.
- Resuming a `force_publish` release still works exactly as before — the
  fallback to `--latest` only activates once the tag genuinely exists, which
  is precisely the resume scenario.
- Tags now consistently reference the commit that actually passed CI, so a
  future audit of "what did CI validate for this tag" no longer depends on
  how fast the job happened to start.
