# History

**Covers:** the project's major eras and why direction changed at each turn —
context for reading the current architecture and the [ADRs](./adr/README.md).
**Excludes:** a changelog of individual releases (see each package's
`CHANGELOG.md`).
**Next:** [adr/README.md](./adr/README.md) for the decisions this history
motivates.

## 1. `openapi-generator`, single package (2025-02 → 2025-08)

Started as a single npm package. The API client was generated by the Java
`openapi-generator-cli` (`typescript-axios`), with a **forked mustache
template** so generated methods returned `data` directly instead of a raw
`AxiosResponse`. Keeping that fork in sync with generator upgrades was
recurring cost, not a one-time one.

## 2. Migration to kubb (2025-08-20)

The forked template existed to work around three gaps: no direct `data`
return, no Zod schema generation, no grouping by OpenAPI tag. kubb supports
all three natively (`dataReturnType: 'data'`, a Zod plugin, `group: { type:
'tag' }`), so the fork was dropped along with the JVM toolchain dependency.
See [ADR-0002](./adr/0002-kubb-client-generation.md).

## 3. A plugin system, built and removed (2025-08 → 2026-02)

A full plugin architecture was added — async initialization, an interceptor
hook, a plugin registry and storage layer, ~1000 lines plus docs. It required
`createMarzbanSDK()` to become async (replacing `new MarzbanSDK()` as the
primary construction path) and kept surfacing type/validation conflicts. No
real plugin beyond two examples was ever built on it, and it was removed
entirely six months later. The factory function it introduced outlived it and
is now the canonical way to construct the SDK. See
[ADR-0007](./adr/0007-plugin-system-removed.md).

## 4. v2.0.0 — classed generated API clients (2026-05-19)

Generated operations were free functions closing over a single global axios
instance, so multiple SDK instances in one process shared one HTTP client.
Switching kubb's client plugin to `clientType: 'class'` let each generated
`*Api` class take a `client` in its constructor, giving each SDK instance its
own. See [ADR-0004](./adr/0004-classed-generated-api-clients.md).

## 5. v3.0.0 — cross-runtime (2026-06-22, breaking)

`node:crypto`, used for webhook signature verification, was a static import
that bundlers pulled into browser builds even when unused. Replaced with Web
Crypto (`globalThis.crypto.subtle`), which made webhook verification async;
`Buffer` usage became `Uint8Array`; runtime detection switched from identity
checks to capability checks. See
[ADR-0006](./adr/0006-cross-runtime-web-crypto.md).

## 6. Quality hardening (2026-06)

Coverage thresholds moved to 100% for hand-written code, config defaults were
centralized, and internal code was switched to consume only `ValidatedConfig`.
See [ADR-0008](./adr/0008-100-percent-coverage.md).

## 7. Monorepo migration (2026-08-10)

Two new artifacts were planned on top of the SDK — an MCP server and a CLI —
which the single-package layout couldn't host cleanly. The repo moved to
pnpm workspaces + Turborepo, with the SDK relocated to `packages/sdk` and
`packages/mcp`/`packages/cli`/`apps/docs` added alongside it. Each publishable
package got its own version, changelog, and tag prefix. See
[ADR-0001](./adr/0001-pnpm-turborepo-monorepo.md).

## 8. The SDK's public API starts responding to an internal consumer (2026-08)

The first case of a package inside this repo — rather than an external
user — driving a change to the SDK's public surface: `packages/mcp` needed a
stderr-only logger stream (stdout is reserved for JSON-RPC), so `index.ts`
gained a `Logger` type export, `ERROR_CODES`, `redactSecrets`, and
`validateConfig` as named exports, and `HttpError` gained typed accessors.

## Where things stand

The monorepo migration lives on `dev` and has not yet merged to `main` — CI
and publish workflows on `main` are still the pre-monorepo, single-package
versions. The `sdk-v*`/`mcp-v*` tag scheme is declared in `publish.yml` but
hasn't produced a tag yet; the most recent actual release tag is `v3.0.1`.
